# Как читать и реализовывать API

## Границы ресурсов

- `/offers` — публичный каталог, `/offers/{offerId}` — карточка без внутренних данных.
- `/venues/{venueId}/batches` и `/venues/{venueId}/offers` — рабочее место сотрудника. venueId проверяется через membership.
- `/orders` — авторизованный покупатель, личность берётся из JWT, а не из buyerId в JSON.
- `/orders/{orderId}/...` — команды над конкретным заказом; доступ определяется ролью, ownership и заведением заказа.
- `/venues/{venueId}/events` и `/analytics` — отчётность сотрудника.

`POST .../publish`, `.../fulfill` и другие команды отделены от PATCH: у каждой свои разрешения, правила и побочные эффекты. Клиент не может прислать произвольный status или totalPriceMinor.

## Пример бронирования

```http
POST /v1/orders
Authorization: Bearer <buyer-jwt>
Idempotency-Key: 3f58cb96-c03c-4f17-bb94-3dafae5db66e
Content-Type: application/json

{
  "offerId": "2f6b4d52-47cb-48a2-aa03-de69feab8dce",
  "quantity": 2,
  "pickupAt": "2026-10-16T18:30:00+04:00",
  "paymentMethod": "AT_PICKUP"
}
```

Пример времени иллюстративный: реальный запрос должен удовлетворять текущему серверному времени и окну конкретного бокса. При 201 ответ Order содержит снимок состава, итоговую цену, NOT_PROCESSED и код выдачи. Сохранять Idempotency-Key до получения определённого результата; сетевой timeout не означает, что бронь не создана.

При 409 INSUFFICIENT_STOCK клиент обновляет доступность и предлагает изменить количество. При 422 PICKUP_TIME_INVALID — выбрать новое время. При 401 — повторно войти. Автоматически повторять мутацию можно только с исходным ключом и неизменённым телом.

## Ошибки бизнес-правил

| code | HTTP | Когда |
|---|---:|---|
| INSUFFICIENT_STOCK | 409 | Не хватает продуктов для публикации или боксов для брони |
| VERSION_CONFLICT | 409 | Черновик изменён другим запросом |
| QUOTE_EXPIRED | 409 | Прошли 5 минут или quote не соответствует версии |
| INVALID_STATE | 409 | Переход из конечного статуса или повторная публикация |
| IDEMPOTENCY_CONFLICT | 409 | Ключ уже использован с другим телом |
| SALE_NOT_ALLOWED | 422 | Сроки, хранение или окно не удовлетворяют правилам |
| PRICE_INVALID | 422 | Цена вне диапазона или нет причины изменения |
| PICKUP_TIME_INVALID | 422 | Время вне окна или слишком близко к now |
| NO_SHOW_TOO_EARLY | 422 | Сотрудник отметил неявку раньше допустимого времени |
| CANCELLATION_TOO_LATE | 422 | Покупатель отменяет после наступления pickupAt |
| INVALID_PICKUP_CODE | 422 | Не совпал код выдачи |
| RATE_LIMITED | 429 | Превышено число запросов или попыток ввода кода |

В OpenAPI ошибки используют общий Error и общий response для уменьшения дублирования. Конкретный HTTP-код и code должны соответствовать этой таблице. default покрывает прочие ошибки, в том числе 401, 403, 429 и 500; наличие общего 409/422 в публичном GET не означает отдельного бизнес-перехода.

## Работа продавца

1. Создать партии через createBatch.
2. Создать черновик через createOffer, сохранив offerId и version.
3. Вызвать quotePrice; показать explanation и рекомендованную цену.
4. Вызвать publishOffer с quoteId, expectedVersion и подтверждённой ценой.
5. Смотреть listVenueOrders с диапазоном pickupAt. По истечении noShowEligibleAt показывать кнопку «Не пришёл»; сервер повторно проверяет время.
6. При выдаче покупатель показывает заказ; сотрудник открывает его по id и вводит сообщённый код в fulfillOrder. Поиск только по коду не предусмотрен: код не уникален глобально.
7. Открыть аналитику. Для раскрытия показателя использовать listVenueEvents с тем же периодом и типом ORDER_FULFILLED/ORDER_NO_SHOW/ORDER_CANCELLED/ORDER_RESERVED; aggregateId ведёт в карточку заказа.

Все POST, включая price-quotes без тела, требуют новый Idempotency-Key для новой операции. PATCH использует expectedVersion вместо ключа. После изменения черновика нужно получить новую рекомендацию.
